# C60: ship the user-requested Gemini side button

On 2026-09-27 the user clarified that the desired feature is the AI button that answers questions and controls the app, then explicitly requested it ready to ship. This supersedes F32's separate-prototype and live-provider deferral, without reopening unrelated feature claims or permitting unsupported data claims. The old `codex-ai-app-control` branch is preserved; F32 resumes from current main on `codex-f32-live-assistant`.

F32 owns its new `/assistant` workspace, UI, provider/API and tests. The technical lead owns this contract and the later shared layout/CI integration. The frontend and Gemini engineers work on disjoint paths under the root; an independent reviewer checks the completed boundaries. No new package is required: use fixed-host Gemini REST with strict JSON output and the existing Zod/runtime.

`GET /api/assistant` reports configuration readiness without billing or exposing credentials. `POST /api/assistant` accepts a bounded message, supported national filters, visible project identifiers and request identifier. Its response identifies action, clarification, deterministic help, unsupported or unavailable, with a validated action or null, a grounded message, echoed request identifier and actual provider/model when used. Server context comes from existing national summaries/reference records; client identifiers are intersected with those records. Source strings are untrusted data. Every action is revalidated at execution against the current UI context. No model-authored numerical facts are accepted as application evidence.

`ASSISTANT_ENABLED=true`, `GEMINI_API_KEY` and `GEMINI_MODEL` enable the provider on the server. Missing configuration produces an explicit unavailable state; no hidden offline-model substitute. The endpoint accepts same-origin JSON requests, bounds request/response size and concurrency, applies a per-process rate budget, uses a fixed Google host and a deadline, and does not log prompts or keys. A process budget is not an account-wide billing cap; deployment must also retain provider-side quotas. Live verification uses only public app context and requires an existing authorized credential source. No credentials are requested in chat or committed.

The global `AssistantHost` wraps the existing children in the shared app layout after the F32 component exists. Its workspace bridge reuses NationalExplorer's controller. From other views, filter/focus commands navigate to the same workspace with supported parameters; approved navigation may open Time, History, coverage, filing changes, field planning, Gemini, impact or home. It does not manipulate arbitrary DOM or edit other feature implementations. Existing Time/History semantics and ownership remain intact. Unknown/ambiguous places, missing records, stale context and provider failure cause clarification or no action.

Acceptance: strict provider/command tests, configured transport integration tests, missing-key real-backend browser readiness, browser action/filter/undo/navigation/clarification/stale-response/mobile/keyboard cases, independent review and exact-revision CI. The local server policy rejection is not bypassed; use the existing GitHub browser runner. Code readiness, live-provider verification and deployment are reported separately. Undo by disabling the provider flag and removing the additive layout host; deterministic app workflows stay available.

The shared-layout follow-on imports F32's accepted `AssistantHost` once around page children. The existing navigation remains in place, and the standalone workspace detects the inherited host to avoid duplicate launchers. Its global browser acceptance case automatically becomes active when this layout integration is present; it must pass unskipped before the app-wide button is reported delivered. This adds no provider credential or deployment-wide spending guarantee.
